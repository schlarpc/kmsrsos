# kmsrs-dbgen

Extracts the product database from Microsoft's own licensing artifacts
(`DB-001`, #125; `DB-002`, #126).

**Data ships through this pipeline or it does not ship** (declined item D19).
Hand-copying values out of another emulator's catalogue is the practice that
produced every fabricated GUID the audits found — including two KMS counted IDs
that appear in no Microsoft artifact and are *valid* UUIDv5, while the genuine
Office LTSC 2024 one has an invalid version nibble.

## Running it

```shell
$ cargo run -p kmsrs-dbgen -- regenerate
```

Then review the diff to `crates/kmsrs-db/data/products.toml` and commit it. This
is never run during a build: a build that reached out to a registry would not be
hermetic, and a data change that appeared without a pull request would not be
reviewable.

`fetch` and `extract` can be run separately. Artifacts land in
`crates/kmsrs-dbgen/artifacts/`, which is **not** committed — the digest of each
source is recorded in the generated file instead, so a silently republished
artifact shows up as a changed digest.

## Where the data comes from

| Source | What it gives |
|---|---|
| `mcr.microsoft.com/windows/servercore:ltsc2025` | `pkeyconfig-csvlk.xrm-ms`, `pkeyconfig.xrm-ms` and the `spp\tokens` tree — every Windows product key configuration, and the counted-ID list per CSVLK |
| Office LTSC 2024 Volume License Pack | `pkeyconfig-office-kmshost.xrm-ms` and the four KMS host licences — the Office 2016/2019/2021/2024 CSVLKs and Office LTSC 2024's counted ID |

Both are public and need no credentials. The Windows layer is about 1.5 GB and
is streamed through gzip and tar without touching disk; only the ~150 licensing
artifacts are kept.

## How the join works

Two artifact families, one join key:

- **`pkeyconfig`** carries a base64 (sometimes gzipped) `ProductKeyConfiguration`
  document inside `<tm:infoBin name="pkeyConfigData">`, with `ActConfigId`,
  `RefGroupId`, `EditionId`, `ProductKeyType` and the `KeyRange` list.
- **Licence files** carry `Security-SPP-KmsCountedIdList`,
  `Security-SPP-CMIDExpirationPeriod` and the application GUID.

They join on `<tm:infoStr name="productSkuId">`, which holds the same GUID as
`ActConfigId`. Matching on that rather than on file names is what makes the
extraction principled: `csvlk-2` means nothing, and the number is not stable
between images.

## What the output is, and is not

`products.toml` is a *transcription*, not an interpretation. It holds every key
type Microsoft ships — `Volume:CSVLK`, `Volume:GVLK`, `Volume:MAK`, `Retail`,
the `OEM:` kinds, the evaluation types — because the distinction between them is
what the product gate is built on (`POL-010`, #98), and because a row present in
the artifact and absent here is a row somebody will later re-derive by hand.

Interpretation happens in `kmsrs-db`'s `build.rs`, which partitions these rows
into the typed tables the server uses and fails the build on any invariant
violation (`DB-003`, #127; `DB-004`, #128).

One inference is made, and it is recorded in the data rather than hidden in the
code: a `pkeyconfig` document names no application, so a Windows image's product
table is attributed to Windows and an Office pack's to Office. It is written on
the `[[source]]` row. A source whose licences named two applications would make
the inference unsound, and extraction stops instead.

## Coverage

The two sources above do not cover every product a client might ask about — an
image ships the CSVLKs that image needs. Windows Server 2022, 2019 and 2016, and
Office 2010 and 2013, need their own sources; that is `DB-010` (#134). The
consequence of a gap is mild by design: an unknown KMS counted ID is still
activated (`POL-010`, #98), it simply logs as a raw GUID.
